# yappang Q4B vs 해찬 8B (v5·v7) 비교 (2026-11-09)

4090 서버를 더 못 쓰는 상황이라, yappang 님이 4060으로 학습한 Qwen3-4B(`stockrule-q4b-v1`, Q8_0 GGUF 4.3GB)를 8B 모델과 같은 시험·같은 채점기로 다시 쟀다.

## 어떻게 비교했나
1. Q4B를 Ollama에 `haechan-cmp-q4b` 이름으로 등록했다(Modelfile 그대로, yappang 폴더 파일은 건드리지 않음).
2. `compare_q4b/run_ollama_eval.py`로 같은 4세트(공식 111, 시험 58, 추가 시험 31, 시험 v7 34)를 보냈다. 시스템·사용자 메시지만, few-shot 없음, temperature 0, thinking 끔. 채점은 `eval_model.py`의 `score`·`summarize`를 그대로 불러 썼다.
3. yappang 자체 보고(필드 정확도 63.7)는 정의가 달라(사용자 지정 지표의 id·operator·value·unit 전부 일치) 숫자를 바로 비교하지 않는다.
4. 결과 원본은 `compare_q4b/{official111,test58,v5set31,v7set34}/`.

## 속도·메모리
- Q4B(Ollama, 4080 Super에서 측정): 건당 평균 3.5~4.8초, 생성 약 340~410토큰, GPU 메모리 약 5.7GB 사용(맥락 4096 포함, 측정값). 4060 8GB에도 들어간다(yappang README: 약 4.8GB).
- 8B(NF4 4비트 + 어댑터): 배치 8로 평가해서 건당 시간을 같은 조건으로 재지 못했다(공식 111건 약 17분). 8B는 4비트 기준 대략 6GB대지만 이번에 직접 재지는 않았다. 8GB 카드에서의 실제 속도는 미확인.

## 장단점
**Q4B 장점**
- 작고 빠르다. 4060 8GB에서 그대로 돈다. 서버 없이 노트북에서 시연 가능.
- JSON은 100% 유효하고, 되묻기 "해야 하는지" 판단은 공식에서 30/30으로 맞췄다.
- 이미 GGUF·Ollama 형태로 있어 앱 연결이 바로 된다.

**Q4B 단점**
- 지표를 정확히 고르는 능력이 크게 낮다(공식 사용자 지정 지표 65.0 vs 97.5). 지표 혼동, 부등호 방향, 값 틀림이 많다.
- 20개 밖 개념을 거절하지 못하고 되묻기로 답한다(공식 거절 14건 중 3건이 되묻기, 새 문장 세트에서는 거절 1/10).
- 학습 데이터가 병준 병합본뿐이라 새 표현에 약하다(시험 3세트에서 8B와 차이가 더 크다).

**8B(v5) 장점**: 추출·거절·되묻기 사유 모두 높고, 새 문장에서도 비교적 유지된다.
**8B 단점**: 무겁다(8GB 카드에서는 빠듯함, 4비트 필요), 학습은 4080 같은 16GB 카드가 필요했다. Ollama용 GGUF 변환 후 양자화가 달라져 다시 재야 한다.

## 주의 (공정성)
- 모델 크기(4B/8B) 효과와 학습 데이터 효과(내 보강 데이터 유무)가 섞여 있다. 차이의 어느 정도가 크기 때문인지는 이 비교로 나눌 수 없다. 같은 데이터로 4B를 다시 학습해야 분리된다.
- 양자화도 다르다(8B는 NF4+어댑터 직접 로드, Q4B는 Q8_0 GGUF/Ollama). 8B를 GGUF로 바꾸면 점수가 달라질 수 있다.
- 시험 문장 수가 적다. 작은 차이는 우연일 수 있지만 이번 차이(20~70%p)는 그보다 크다.
- 호출 방식(format=json 제한 여부)이 yappang 자체 평가와 달라 그쪽 숫자와 다를 수 있다.

## 판단
정확도가 목표라면 8B(v5 3ep)를 쓰고, 8B를 못 돌리는 환경에서는 Q4B가 "돌아가는 대안"이지만 정확도 손실이 크다. 4B로 가려면 내 보강 데이터(v6/aug)를 포함해 4B를 다시 학습해 보는 것이 다음 단계다(이번에는 하지 않음).
