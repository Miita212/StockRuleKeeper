## 3. 모델 선택 검토

이 3개 자료에는 사용할 모델이 정해져 있지 않다. 그래서 선택지를 비교하고 기준을 제시한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 외부 상용 LLM API (프롬프트 + JSON 출력 강제) | 가장 빨리 시작, 한국어 품질이 높고 구조화 출력 지원 [일반] | 호출 비용·지연, 외부 키 관리 필요, 시연 중 네트워크 의존 |
| B. 오픈 가중치 모델 (예: 7B급) 자체 구동 | 비용 예측 쉬움, 오프라인 가능 [일반] | GPU 필요, 한국어·JSON 정확도는 튜닝이 필요 |
| C. B를 M1·M3에만 파인튜닝 | 출력 형식 고정 작업에 효과적 [일반] | 데이터 제작·학습 시간. 10일 MVP에서는 부담 |

**권고 [제안]:** (하드웨어 조건 확정 전 초안) A로 먼저 기준선을 만들고 B/C를 비교한다. → **3.1의 하드웨어 조건이 확정되어 아래처럼 갱신한다.** 어느 경우든 한 모델에 의존하지 않도록 `api/index.ts` 뒤에서 모델을 교체할 수 있게 둔다.

### 3.1 추가 조건 (2026-11-04 사용자 제공): 학습 RTX 4090, 추론 노트북 RTX 4060

이 조건은 **사용자가 알려준 사실**이다. VRAM 수치와 속도는 [일반] 상식에 따른 추정이며 실측 전에는 확정이 아니다.

| 구분 | 장비 | VRAM [일반] | 의미 |
|---|---|---|---|
| 학습 | RTX 4090 | 24GB | 7~8B급 LoRA/QLoRA 학습이 여유 있다 |
| 추론 | 노트북 RTX 4060 | **8GB** (노트북·데스크톱 모두 8GB) | **모델 크기의 상한을 정하는 쪽은 추론 장비다** |

**1) 모델 크기 상한 = 8GB에 들어가는 크기**
- 7~8B 모델을 16비트로 올리면 가중치만 약 15~16GB라 **4060에 못 올라간다.** 4비트 양자화(약 4~5GB) + KV 캐시(+1GB 안팎)면 8GB에 들어간다.
- 14B급은 학습은 4090에서 가능하지만 4비트로도 약 8~9GB라 4060 추론이 어렵다. → **14B 이상은 후보에서 제외.**
- 3~4B급은 4비트로 약 2~3GB라 여유가 크고, 같은 노트북에서 프론트·백엔드·DB를 함께 띄울 때 유리하다.
- 결론: **후보는 3~8B급 오픈 모델을 4비트 양자화해 4060에서 구동하는 안**이다. 이전 3장의 B/C안이 주력이 되고, A(외부 API)는 비교 기준선·대체 수단으로 내려간다.

**2) 학습과 추론의 엇갈림을 줄이는 방법**
- 학습은 4090에서 QLoRA(또는 bf16 LoRA)로 하고, 학습 뒤 어댑터를 합쳐 **4비트 형식(예: GGUF Q4_K_M)으로 변환**해 노트북에서 돌리는 흐름을 권한다 [제안].
- **양자화로 품질이 떨어질 수 있으므로** 평가 세트(5장)를 ① 양자화 전(4090) ② 양자화 후(4060) 두 번 돌려 차이를 확인한다. 이 항목은 원칙 해석처럼 정확한 JSON이 필요한 작업에서 특히 중요하다.
- 추론 실행기 후보 [일반]: llama.cpp 계열(Ollama 포함)이 8GB급 GPU에서 쓰기 쉽고 JSON 스키마·문법 제약 출력을 지원한다. vLLM은 Windows 노트북에서는 설치 부담이 있다. 실제 선택은 노트북 OS와 설치 시험 뒤에 정한다.

**3) 속도 감각 [일반, 실측 필요]**
- 4060 노트북의 메모리 대역폭을 감안하면 7B 4비트는 대략 초당 수십 토큰 수준으로 예상된다. 원칙 해석 출력(JSON 100~150토큰)은 몇 초 안에 끝날 것으로 보이나 **반드시 실측**한다.
- 노트북은 열·전원 설정에 따라 성능이 떨어질 수 있다. 시연 때는 전원 연결·고성능 모드를 확인한다.
- 입력이 길어지면(20개 지표 목록을 프롬프트에 넣을 때) 첫 토큰이 늦어지므로, 파인튜닝으로 지표 목록을 모델에 내재화하면 프롬프트를 줄일 수 있다 [제안].

**4) 모델 후보 [일반 — 최신 여부·라이선스는 선택 전에 확인 필요]**
한국어가 가능한 3~8B급 오픈 모델을 후보 풀로 둔다. 예: Qwen 계열 7B/4B급, EXAONE 계열 7~8B급, Gemma 계열 4B급. 이 문서는 특정 모델을 확정하지 않는다. 선택 기준은 ① 한국어 JSON 출력 안정성 ② 4비트 양자화 후 품질 하락 폭 ③ 라이선스(상업·배포) ④ 4060에서의 실측 속도이고, **같은 평가 세트로 후보 2~3개를 비교**해 정한다.

**4-1) 후보 3개 비교와 1순위 추천 (한국어 지원 중시)**

조건: 4060 8GB에서 4비트로 구동 가능, 4090에서 QLoRA 학습 가능, 한국어 지원. 아래 점수·수치는 **내 일반 지식에 기반한 상대 평가이며 실측이 아니다.** 웹 검색으로 확인한 것은 일부뿐이라 표에 따로 표시했다.

| 항목 | **Qwen3-8B** | **EXAONE 3.5 7.8B Instruct** | **Gemma 3 4B (instruct)** |
|---|---|---|---|
| 개발사 | Alibaba | LG AI Research | Google |
| 크기 / 4비트 VRAM [일반] | 8.2B / 약 5~6GB | 7.8B / 약 5GB | 4B / 약 3GB |
| 한국어 | 다국어 모델, 한국어 양호 (검색 가이드가 한국어용 추천 목록에 올림, 점수는 미확인) | **한국어 특화**, 한국어 벤치마크 강점 (3.5 7.8B KMMLU 44.58, 검색 결과) | 다국어 양호하나 크기가 작아 복잡한 지시에 약할 수 있음 |
| JSON·지시 따르기 [일반] | 강함 (구조화 출력·도구 호출에 강점) | 보통~양호 | 보통 |
| 미세조정 생태계 [일반] | 매우 풍부 (QLoRA·GGUF 변환 사례 많음) | 가능하나 사례 적음 | 풍부 |
| 라이선스 | Apache-2.0 계열로 알고 있음 → **모델 카드에서 확인 필요** | **연구·비상업 중심** (검색 결과: 공식 카드 확인 필요, 일부 미러에 완화 공지) | Gemma 이용약관 (사용 제한 조항 있음) |
| 4060 속도 [일반] | 중간 | 중간 | **가장 빠름** |
| 주의점 | 사고(thinking) 모드를 꺼야 지연이 짧다. 한국어 문체가 가끔 번역투일 수 있음 | 라이선스가 걸리면 배포(앱인토스) 시 문제 | 학습·평가에서 정확도 한계가 먼저 올 수 있음 |

**1순위 추천: Qwen3-8B**
- 이유 ① 이 앱의 모델 작업은 "한국어 문장 → 정해진 JSON"이라 한국어 문체의 자연스러움보다 **한국어 이해 + 구조화 출력 안정성**이 먼저다. Qwen3-8B가 이 둘의 균형이 가장 좋을 것으로 본다 [제안].
- 이유 ② 8B 4비트가 4060 8GB에 들어가고, 4090에서 QLoRA 학습이 쉽다. 학습 자료·도구가 가장 많아 10일 일정에 유리하다.
- 이유 ③ 라이선스 부담이 상대적으로 적다 [확인 필요].
- 한국어 말투("~해요")가 어색하면 M4 설명 문구 단계에서만 후처리하거나, 파인튜닝 데이터에 해요체 예시를 충분히 넣는다.

**2순위: EXAONE 3.5 7.8B** — 한국어 품질은 가장 좋을 가능성이 크지만 라이선스 때문에 앱인토스 배포를 염두에 두면 위험하다. 학교 과제·시연 범위라면 같은 평가 세트로 Qwen3-8B와 겨뤄 볼 가치가 있다.
**3순위: Gemma 3 4B** — 가볍고 빠르다. 8B 모델이 노트북에서 느리거나 다른 서버와 VRAM 충돌이 나면 대안이 된다.

**검증 방법 (이 순위를 확정하기 전에 반드시):** 평가 세트(5장) 50문장으로 3개를 같은 프롬프트로 돌려 ① JSON 유효율 ② 지표·값 정확도 ③ 한국어 말풍선 자연스러움(팀원 3명 이상 평가) ④ 4060 응답 시간을 비교하고, 순위가 바뀌면 이 절을 고친다.

**5) 학습 데이터**
- 4090이 있어도 병목은 데이터다. 학습 데이터는 사람이 만든 소량 씨앗(01의 추천 문구 5개, 기획보고서 사례)을 바탕으로 **외부 LLM으로 다양화해 생성**하는 방법을 쓸 수 있다 [제안]. 이때 사용하는 외부 서비스의 약관(생성물로 다른 모델을 학습해도 되는지)을 확인해야 한다.
- 평가 세트는 학습 데이터와 겹치지 않게 따로 만든다.

**6) 배포 구조에 미치는 영향**
- 추론이 노트북 한 대에서 도므로 **시연 구성은 "노트북이 모델 서버 + 백엔드"**가 된다. 프론트(에뮬레이터/기기)가 노트북의 주소로 호출해야 한다. UI 문서의 에뮬레이터 주소(`10.0.2.2:5173`)는 프론트용이고, 모델 서버 주소·포트는 별도로 정해야 한다 [제안].
- 앱인토스 실제 배포까지 가려면 사용자 기기에서 접근 가능한 서버가 필요한데, 노트북 추론은 **시연·MVP 범위**에 적합하고 상시 서비스에는 맞지 않는다 [일반]. 배포 요건 확인은 7장 8번 항목이다.
- 외부 API(A안)는 노트북 모델이 실패했을 때의 **예비 경로**로만 남긴다. 키 관리 주의는 4장과 같다.

## 4. 파이프라인과 입출력 [제안]

```
사용자 입력(01)
  → [모델] 지표·방향·기준값 추출 (JSON Schema 강제)
  → [코드] 검증: 지표가 20개 안에 있는가 / 값이 허용 범위인가 / 방향이 맞는가
  → 부족·모호 → [모델] 되묻기 문구 + 선택지 3개 (02-1) → 사용자가 선택/직접 입력 → 반복
  → 충분 → [코드] 20개 기준값 구성 → [모델] 설명 말풍선 (02)
  → 사용자 승인("이 원칙으로 시작해요")
```

M1 출력 예시:
```json
{
  "needs_clarification": true,
  "clarification": {
    "message": "빚이 많다는 건 보통 부채비율이 높다는 뜻이에요.",
    "options": [
      {"label": "업종 평균인 100% 이하면 괜찮아요", "value": 100},
      {"label": "50% 이하로 더 엄격하게 할래요", "value": 50},
      {"label": "200%까지는 괜찮아요", "value": 200}
    ]
  },
  "indicators": [
    {"id": 1, "name": "부채비율", "operator": "<=", "value": 100, "unit": "%", "confidence": 0.9}
  ]
}
```
M3 출력 예시: `{"changes":[{"id":1,"name":"부채비율","before":100,"after":80,"unit":"%"}]}` (14 화면의 "바뀐 내용" 카드와 같은 모양).

- 함수 이름·JSON 형식은 임시안이다. 확정 시 팀과 맞춰 `docs/interface.md`에 올려야 한다(내가 직접 수정하지 않음).
- 검증 코드는 필수다. 모델이 20개에 없는 지표(예: ROE)나 비정상 값을 내놓아도 걸러진다.
- 값이 비는 지표는 모델이 채우지 않고 UI 문서의 기본값 표를 쓴다. 이 표는 임의값이라 팀 검토가 선행되어야 한다 [B].
- 앱 보안 [일반]: 외부 API 키는 클라이언트(앱)에 넣지 않고 서버 쪽에서만 호출한다. 키는 `.env`로 관리하고 커밋하지 않는다(CLAUDE.md 규칙).

## 5. 평가 계획 [제안]

- 평가 세트: 직접 만든 50~100문장. 구성: 01의 추천 문구 5개, 기획보고서 사례(빚 많은 회사 회피 등), 구어체·줄임말·오타, 20개에 없는 요구, 지표와 무관한 말.
- 지표: ① 지표 선택 정확도 ② 기준값 정확도 ③ JSON 유효율 ④ 되묻기 필요 여부 판별 정확도 ⑤ 응답 시간.
- 목표치는 정하지 않았다. 기준선 측정 후 팀과 정한다.
- 수정(M3) 평가: 상대 표현("더 낮춰", "조금 느슨하게")이 합리적인 폭으로 바뀌는지 샘플 점검.

## 10. 파인튜닝 데이터 준비 (1순위 Qwen3-8B 기준) 와 주식 용어 검토

추가일: 2026-11-04. 근거 표기는 앞 장과 같다. 웹 검색으로 확인한 것은 **[검색]** 으로 따로 표시했다.

### 10.1 먼저: 무엇을 학습시키는가

파인튜닝은 "주식 지식을 가르치는 것"이 아니라 **초보자의 말을 정해진 지표·기준값 JSON으로 안정적으로 바꾸는 것**이 목적이다(2장 M1~M3). 따라서
- 지표 정의·기준값·업종 평균 같은 **사실은 사전(JSON)에서 주입**하고 모델의 기억에 맡기지 않는다. (UI 문서의 "업종 평균은 100% 안팎" 같은 문구도 근거 출처가 문서에 없다 → 사전에 근거와 함께 기록해야 한다.)
- 모델은 **말 → 지표 매핑, 방향·단위 판단, 되묻기 여부, 해요체 설명**을 학습한다.
- 지표 20개는 이미 6개 → 20개로 한 번 바뀐 이력이 있다 [B]. 목록을 가중치에만 넣으면 바뀔 때 재학습이 필요하므로, **시스템 프롬프트에 간단한 지표표(id·이름·방향)를 항상 넣고 학습한다** [제안].

### 10.2 주식 용어: 왜 중요하고 무엇이 위험한가

| 위험 | 예 | 대응 |
|---|---|---|
| 구어체 ↔ 공식 용어 간극 | "빚 많은 회사" → 부채비율, 차입금의존도, 이자보상(EBITDA/금융비용) 중 무엇인가 | 구어체 동의어 사전 + 되묻기 규칙 |
| 같은 말이 여러 지표 | "비싸다" → PER, PBR, 52주 고점 대비. "안정적" → 변동성, 부채비율, 연속 흑자 | 포괄 표현 → 지표 묶음 규칙을 팀이 정함(7장 5번) |
| 방향(좋은 쪽) 혼동 | 부채비율은 낮을수록, 배당수익률은 높을수록 좋음. 자본잠식률 "0% 이하" | 지표마다 `operator`를 사전에 고정, 모델이 뒤집으면 검증 코드가 차단 |
| 표현의 방향어가 문서마다 다름 | UI 문서 기준값에 "이하·이상"과 "이내"가 섞임(예: 52주 고점 대비 "−20% 이내", 저점 대비 "50% 이내") | **`이내`의 정확한 부등호를 정해 통일** (미정 → 팀 확인) |
| 단위 혼동 | %, 배, 년, 원/억/조원 (시가총액 1조원, 거래대금 10억) | 사전에 `unit`·허용 범위 필수, 학습 데이터에 단위 변환 예시 포함 ("1,000억" → 1000억원) |
| 영문 약어 | PER·PBR·EBITDA 등은 한글명(주가수익비율)과 병기됨 [B] | 한글/약어/UI 표기 별칭표를 한 곳에 두고 학습 데이터에서 섞어 사용 |
| 기간 용어 | 최근 12개월, 60거래일, 20거래일 | 사전에 기간 필드 분리, 시뮬레이션 기간(1·3·6·12개월)과 구분 |
| 모델의 용어 지식 부족 | 8B급이 "자본잠식률", "차입금의존도" 정의를 틀릴 수 있음 | **학습 전에 용어 진단 테스트(10.5)로 확인 → 부족하면 정의 문장을 프롬프트에 주입 + 학습 데이터에 정의 질의응답 추가** |
| 환각 | 없는 지표(ROE 등), 틀린 업종 평균 | 20개 화이트리스트 검증, 사실은 사전 주입 |

Qwen3-8B의 한국어 금융 용어 지식은 **이번 검토에서 확인하지 못했다.** 10.5의 진단 테스트로 학습 전에 직접 재야 한다.

외부에서 받을 수 없고, 이 앱에 맞춘 것이라 팀이 만들어야 한다.

| # | 산출물 | 내용 | 규모 [제안] | 담당·검수 |
|---|---|---|---|---|
| H1 | **지표 마스터 JSON** | 20개 각각: `id`, 공식 이름, UI 표기, 약어, 영역, `operator`(고정), `unit`, 허용 범위, 기본값, 한 줄 정의, 계산식 개요, 상대 표현 증감폭 | 20행 | 금융 지식이 있는 팀원 1명 작성 + 다른 1명 검수 |

### 10.4 다운로드·수집해서 쓰는 것 (참고·보강)

공개 자료는 **용어·정의·평가 참고용**이다. 이 앱의 출력 형식(JSON)과 다르므로 그대로 학습 데이터가 되지는 않는다. 사용 전에 각 자료의 **라이선스와 이용조건을 직접 확인**해야 한다.

### 10.5 자동 생성(합성)하는 것

H1~H4를 바탕으로 늘린다. 4090으로 학습하는 모델 크기와 별개로, 생성은 외부 LLM 또는 로컬 큰 모델(4090 24GB에 양자화로 올라가는 범위)을 쓸 수 있다 [제안]. **외부 서비스 생성물로 다른 모델을 학습하는 것이 약관상 허용되는지 먼저 확인한다.**

| # | 유형 | 방법 | 목표 개수 [제안] |
|---|---|---|---|
| S1 | 원칙 해석 변형 | H4 시드를 존댓말·반말·줄임말·오타·영어 약어·감정 표현으로 다양화 | 1,500~3,000 |
| S2 | 복수 지표·포괄 표현 | "안전하고 배당 좋은 회사" 같은 조합 | 300~500 |
| S3 | 되묻기 대화 (여러 턴) | 모호한 입력 → 설명+선택지 3개 → 선택/직접 입력 → 확정 | 300~500 |

### 10.6 학습 전 용어 진단 테스트 (먼저 할 일)

학습 데이터를 만들기 전에 Qwen3-8B(그리고 비교 후보 2개)에 아래를 돌려, **용어 지식이 어느 지표에서 약한지** 먼저 본다.

1. 지표 20개 정의 질문(채점: 사전의 정의와 일치)
2. 좋은 방향 질문("부채비율은 높을수록 좋은가?")
3. 구어체 → 지표 매핑 질문(H2 일부 사용)
4. 단위·기간 질문
- 약한 지표는 S6·H2를 늘려 집중 보강하고, 심하면 프롬프트에 정의를 주입한다.
- 이 결과가 모델 순위(3.1절 4-1)를 바꿀 수 있다. 한국어 금융 용어 이해가 특히 약하면 EXAONE 같은 한국어 특화 모델이 유리해질 수 있다.

### 10.7 학습 형식·분할·보관 [제안]

- 형식: Qwen3 채팅 템플릿의 `system`(지표표+규칙) / `user` / `assistant`(JSON). 사고(thinking) 모드는 끄고 학습·추론한다.
- 분할: 학습 / 검증 / 평가 = 약 8 : 1 : 1이되, 평가는 H5를 별도로 쓴다.
- 데이터 규모 감각: 합쳐서 3,000~5,000개면 4090 QLoRA로 짧게 반복 실험이 가능한 수준일 것으로 본다 [일반, 실측 필요].
- 보관: 데이터·모델은 `members/yappang/` 안에 두되 **대용량이라 커밋하지 않는다**(팀 규칙). 마스터 JSON과 가이드 문서처럼 작은 것만 커밋 대상이다. 지표 마스터는 `docs/interface.md`에서 다른 담당자와 형식을 맞춘다.
- 개인정보: 학습 문장에 실제 이름·계좌·실투자 정보를 쓰지 않는다.

### 10.8 작업 순서 (10일 MVP 기준) [제안]

1. H1 지표 마스터 + `이내` 등 방향어 통일 (팀 확인)
2. 10.6 용어 진단으로 후보 모델 용어 이해 점검
3. H2 동의어 사전, H3 되묻기 정책, H6 가이드
4. H4 시드 + H5 평가 세트 (작성자 분리)

6. QLoRA 학습 → 4비트 변환 → 평가(양자화 전후)
7. 약한 지표를 보강 데이터로 재학습

### 11.3 M1 출력 구조를 바꿔야 하는 이유와 초안

PDF의 02 화면은 20개 지표를 카테고리별(재무 건전성 4, 수익성 3, 성장성 2, 가치 2, 배당 2, 규모 1, 주가·거래 6)로 보여 주고 카드마다 기준값과 자물쇠가 있다 [PDF]. 따라서 M1 출력은 다음이 필요하다.

```json
{
  "needs_clarification": false,
  "anchors": [ {"id": 1, "reason": "빚 많은 회사는 피하고 싶어"} ],
  "indicators": [
    {"id": 1, "operator": "<=", "value": 100, "unit": "%", "source": "user", "locked": false},
    {"id": 2, "operator": "<=", "value": 30,  "unit": "%", "source": "default", "locked": false}
  ],
  "explain_bubble": "빚 걱정을 줄이려고 부채비율을 100% 이하로 잡았어요. …",
  "explain_card": "'빚 많은 회사는 피하고 싶어'라는 말을 부채비율 100% 이하로 바꿨어요. 나머지 19개는 …"
}
```
- `source`: `user`(사용자 말에서) / `default`(기본값 표에서) / `inferred`(모델 판단). **기본값은 모델이 만들지 않고 마스터(H1)에서 가져온다.**
- 02 화면에서 어떤 지표를 앵커로 보여 주는지(부채비율만 강조되는 듯함 [추론])는 팀이 확인한다.
- `locked`: 수정(M3)과 시뮬레이션에서 바뀌면 안 되는 지표. **M3 입력에도 `locked` 목록이 들어가고, 출력이 잠긴 지표를 바꾸면 검증 코드가 거절한다.**

| 알아두세요 / 스스로 판단해 보세요 | 3개 주의 문구, 3개 질문 | 고정 문구에 가까움 |

- 이 화면은 "종목 추천"을 의도적으로 피하는 설계다: "과거 결과는 앞으로를 보장하지 않아요", "오르고 내린 이유까지는 알 수 없어요", "스스로 판단해 보세요", "예시 데이터예요" [PDF]. **학습 데이터 가이드(H6)에 이 톤을 규칙으로 넣는다**: 원인 단정 금지, 미래 예측 금지, 특정 종목 매수/매도 권유 금지, 표본 한계(종목 수가 적음) 언급.
- **숫자 일치 검증**: 생성 문장 속 숫자와 종목명이 입력 데이터와 한 글자도 다르면 폐기하는 자동 검사(S8의 필수 검증)를 둔다. 환각 위험이 가장 큰 화면이다.
- "알아두세요", "스스로 판단해 보세요"의 고정 문구는 모델이 생성하지 않고 템플릿으로 둔다 [제안]. 모델 생성은 제목·변경 요약·종목 변화 3블록으로 한정한다.
- 이 화면의 수치는 "예시 데이터"로 표시되어 있고 [PDF] **실제 산출 방식은 미정**이다. 모델 데이터는 입력 JSON 형식만 정해 두면 산출 방식이 바뀌어도 재사용된다.

추가 데이터: **S8 리포트 서술**(입력 JSON → 3개 블록 텍스트) 300~500개 [제안], **H8 리포트 톤 가이드와 금지 표현 목록**(사람 작성).

### 11.5 주식 용어·지표 표기 — PDF에서 새로 발견된 점

| 발견 | 근거 | 대응 |
|---|---|---|
| **같은 지표의 이름이 화면마다 다름**: 원칙 카드에 "매출 성장률 15% 이상 외"(06 원칙 리스트), 지표 카드엔 "매출액 증가율"; "배당수익률 2% 이상"(원칙 카드) vs "12개월 배당수익률"; PER은 02에서 "주가수익비율", 04에서 "주가수익비율 (PER)" | PDF 06·02·04 화면 | **별칭표**(H1/H2)에 정식명·UI명·약칭·원칙 카드 요약명을 모두 등록하고, 모델 출력은 항상 `id`만 쓰고 이름은 코드가 붙인다 |
| 연산자가 4종: **이하 / 이상 / 이내 / 초과** (11 화면 스테퍼 라벨) | PDF 11 | 마스터 `operator`는 4종 + 부호 규칙 필요. 06 문서에서 미정이던 `이내` 해석의 근거가 PDF에 있다(다음 행) |
| **`이내`의 의미**: 52주 고점 대비 "−20% 이내" 기준에 실제값 −8.1%가 **충족**, 52주 저점 대비 "50% 이내"에 +38%가 **충족**, 변동성 "2% 이하"에 2.6%가 미충족 | PDF 04 판정서 | `이내` = **그 방향의 변화폭이 한도 이하**로 읽힌다 [추론]: 고점 대비는 −20% 이상(떨어진 폭 ≤ 20%), 저점 대비는 +50% 이하. 지표마다 부등호 방향이 다르므로 **마스터에 지표별 정확한 부등호를 명시**하고 팀 확인(10.9 항목의 해답 후보) |
| **"흑자" = 영업이익 0억 초과**: 02 카드는 "흑자", 11 스테퍼는 "초과 0억", 04 판정서는 "기준 흑자" | PDF 02·04·11 | 사용자의 "적자 기업은 제외할래요"(01 추천 문구)는 영업이익 `> 0`으로 매핑. 모델 학습 예시에 이 대응을 명시 |
| 방향어가 사용자 말과 반대로 보이는 경우: "빚 **적은**" ↔ 부채비율 **이하** | PDF 06 | 극성 반전 예시를 학습 데이터에 포함 |
| 사용자 추천 문구 5개의 1:1 지표 매핑: 빚→부채비율, 배당 꾸준→연속 배당 연수·배당수익률, 비싼 주식→PER/PBR(가치) [추론], 적자→영업이익, 성장→매출·영업이익 증가율 | PDF 01 | 시드 데이터(H4)의 첫 5건으로 사용. 이 매핑이 맞는지 팀 확인 |
| "성장성도 보고 싶어"(08 칩): 이미 20개 전체를 쓰는 원칙에서 **무엇을 바꾸는 요청인지 불분명** | PDF 08 | 팀 확인. 원칙이 일부 지표만 쓰는 경우(5·4·3개짜리 원칙, 06 화면)에서는 "지표 추가"일 수 있음 |

### 11.6 모델·데이터 계획에 미치는 영향 요약

- **모델 선택(3장)**: 변함없이 Qwen3-8B 1순위. 다만 작업이 "지표 추출"에서 "세트 구성 + 설명 + 리포트 서술"로 넓어졌으므로 평가 항목에 **서술 품질(해요체, 숫자 일치)** 을 추가한다.
- **파인튜닝 범위**: M1(세트 구성)·M2(되묻기)·M3(수정+잠금 준수)는 파인튜닝 대상. M4·M7(설명 문구)과 S8(리포트)은 **파인튜닝 + 템플릿 슬롯 채우기 병행**을 권한다 [제안]. 리포트는 데이터가 부족하면 프롬프트 방식으로 먼저 시험한다.
- **평가 세트(H5)에 추가**: 잠금 지표를 건드리는 수정 요청(거절/우회 확인), 리포트 숫자 일치 테스트, "원인 단정" 유도 질문에서 단정하지 않는지.
- **UI 팀과 맞출 것**: 02 화면의 자물쇠 규칙, 앵커 지표 표시 방식, 13 화면 블록 구조(위 표)를 `docs/interface.md`의 출력 JSON과 맞춘다.

### 11.7 PDF로도 확인되지 않은 것

- 인터랙션(탭 시 전환, 오버레이 설명 화면)과 프로토타입 동작은 PDF가 정지 화면이라 알 수 없다.
- 02의 "아이콘을 누르면 자세한 설명이 나와요" 설명 화면은 PDF에도 없다(M5 용어 설명의 화면 근거 없음).
- 13 화면의 아래쪽 일부 블록(종목 변화·알아두세요·질문)은 PDF에서 텍스트로 확인했고 이미지로는 일부만 확인했다.
- 06 문서가 말한 "설정" 탭, 개별 종목(09)은 PDF에도 모델 관련 내용이 없다.
