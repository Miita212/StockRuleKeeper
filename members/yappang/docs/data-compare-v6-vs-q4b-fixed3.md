# 학습 데이터 비교: 팀 data_v6(haechan) vs Q4B fixed-3

작성: 2026-11-09, yappang. 목적: 8B와 4B가 **같은 데이터**를 쓰기로 한 팀 합의에 따라, 통합 전에 두 데이터의 차이를 확인한다.
비교 대상: `members/zips/data_v6-haechan/data_v6/`(train 5,603 / val 319대화) ↔ `train_model_q4b/data/train_fixed3.jsonl`·`val_fixed3.jsonl`(train 6,439 / val 337대화, q4b-v3 학습에 사용).
방법: 첫 사용자 발화로 문장을 맞추고 전체 대화·정답을 대조했다. `data/scripts/data_fixes.py`(우리 수정 규칙)를 v6에 적용해 보았다. 수치는 모두 직접 센 **측정값**이다. 해석은 "해석"으로 표시했다.

## 1. 결론 먼저

1. **두 데이터는 같은 뿌리(병준 병합본)에서 갈라졌다.** 문장의 약 80%(4,818개)가 공통이다. 공통 문장 중 4,362개는 대화까지 완전히 같다.
2. **차이는 세 갈래다.**
   - (가) 우리 `data_fixes` 수정(부등호·조사)이 v6에 **아직 안 들어갔다.** v6에 규칙을 적용하면 91건이 수정되고 25건이 제외 대상이다. 수정 결과는 q3와 **89건 모두 일치**한다(불일치 0).
   - (나) v6에는 **팀 결정(B4 저점 반등, B6 연속 배당)과 haechan 보강**이 있고, q3에는 없다. 되묻기 유형 정답이 **33개 문장에서 서로 반대**다.
   - (다) q3에는 **지표 모호 되묻기 보강 약 830건**(내부 생성 + 외부 LLM 426)이 있고 v6에는 없다. v6에는 haechan 보강 약 430건(부등호·끝말·되묻기)이 있고 q3에는 없다.
3. **통합 방향 제안:** v6를 기준으로 삼고, ① 우리 수정 규칙 적용, ② 되묻기 33건은 팀 기준(v6)을 따름, ③ 지표 모호 보강은 비중을 조절해 일부만 추가. 근거는 아래 3~5절. 최종 결정은 팀 합의 사항이다.

## 5. 평가 오염 점검
- 평가 문장과 동일한 학습 문장: 양쪽 0건.
- 평가에서 나온 개념어가 학습 문장에 있는 정도: 가성비 v6 2 / q3 0, 빚 걱정 1 / 0, 잘 버는 1 / 0, 롤러코스터·튼튼·ROA·EPS·PEG 등은 양쪽 거의 같다(병합본 유래).
- 우리 원칙(v3까지): 평가 개념어를 보강에 쓰지 않는다. v6의 `gen_aug_v6.py`·`gen_aug_haechan.py`는 평가 오답 유형을 보고 만든 보강이어서(`LABEL_AUDIT.md` 1절의 "틀린 12건과 비교"), **8B 쪽 평가 점수가 오르는 효과와 일반화를 구분하기 어렵다**(해석). 4B와 통합하면 4B 평가도 같은 영향을 받으므로, 통합 후 비교는 별도 시험 세트(haechan 시험 58·31·34)로 하는 것이 안전하다.

## 6. 통합할 때 할 일 (제안)

1. **기준 데이터:** v6 (팀 결정 B4·B6와 haechan 보강 포함).
2. **우리 수정 규칙 적용:** `data/scripts/data_fixes.py`를 v6에 적용(수정 91, 제외 25). 거절 문구 조사 20건 포함. 적용 결과가 q3와 일치함은 확인했다.
3. **후보 키 통일:** `name` 942건 → `label`(q3 방식, 평가 정답 형식). 백엔드는 둘 다 읽으므로 동작에는 영향 없다.
4. **지표 모호 보강 처리:** q3의 지표 모호 되묻기(829문장)를 전부 넣으면 v6 대비 비중이 2.9배가 된다. v4 계획의 "비중 조절 실험"과 맞물리므로, 먼저 일부(예: 약 300~400건)만 추가하고 대조쌍(지표 하나 vs 여러 개)을 같이 넣는 안이 있다. 넣을지, 얼마나 넣을지는 팀 결정.
5. **33건 되묻기 충돌:** B4·B6·규모는 v6를 따르고, 변동성·이자 부담·변동이 큰 주식 3개 표현은 팀이 정한다.
6. **v6 전용 haechan 보강 458문장**은 그대로 포함(평가 문장과 동일한 것 없음).
7. **val:** v6 319 + 우리 val 중 v6에 없는 문장을 합칠지, v6 val 그대로 쓸지 결정(8B와 같은 val이어야 eval_loss 비교가 가능).
8. 통합본을 `fixed-4`로 만들고 `DATA_VERSION.md`에 해시·변경 이력을 남긴 뒤, 8B·4B가 **같은 파일**(sha256)로 학습한다. 8B는 학습 스크립트가 다르므로 haechan과 파일 형식(`messages`)·system 프롬프트가 같은지 확인한다(이 비교에서는 같았다).

## 7. 한계

# 부록: "우리 것(fixed-3)을 기준으로 v6를 반영"하는 안 검토 (2026-11-09)

사용자 제안: ① 기준은 우리 데이터, ② v6의 팀 결정(되묻기 유형 33건)을 우리 것에 반영, ③ v6 전용 보강도 우리 것에 반영. 6절의 "v6 기준" 안과 비교한다. 아래는 임시 폴더에서 시뮬레이션한 **측정값**이다(프로젝트 파일은 만들지 않음).

## A. 시뮬레이션 결과 (fixed-3 + ② + ③ = 가칭 fixed-4)

| 단계 | 내용 | 결과 |
|---|---|---|
| 기준 | fixed-3 train 6,439대화 | 우리 수정 규칙·`label` 키가 이미 적용되어 추가 작업 없음 |
| ② 33건 교체 | 유형이 반대인 33개 문장을 v6의 정답으로 교체 | 대화 수 변화 없음(33↔33). 교체한 33개는 모두 단일 턴. `name`→`label` 변환 필요 |
| ③ v6 전용 추가 | v6에만 있는 458행 중 **433행 추가, 25행 제외** | 제외 25행은 우리 `data_fixes`의 의미 반전·깨진 문장(예: `영업이익이 0억원 이상인 회사는 없애고 싶어요`). 추가분: 추출 326, 거절 63, 값 되묻기 24, 지표 모호 14, 기간 6. 수정 후 추가는 2행 |
| 결과 | **train 6,872대화** | 평가 문장과 동일 0건, 첫 문장 기준 train과 val 겹침 0건 |

통합 후 응답 분포: 추출 3,124 / 거절 536 / 값 되묻기 1,698 / **지표 모호 1,268** / 기간 72 / 용어 설명 599.

## B. 이 안이 맞는 이유
- **무손실에 가깝다.** 우리 수정 규칙 결과(89건 일치)가 그대로 유지되고, v6의 팀 결정과 haechan 보강만 얹는다. v6 기준 안은 수정 91건을 다시 적용하고 후보 키 942건을 변환해야 하지만, 이 안은 33건 + 433건만 처리한다.
- **B4·B6 일관성이 해결된다.** 교체 전 우리 데이터는 같은 표현군이 둘로 갈려 있었다(예: 배당 꾸준 → 연속 배당 연수 값 되묻기 38 : 지표 모호 13, 바닥·저점 반등 → 값 되묻기 12 : 지표 모호 8). 교체 후 배당은 13번 값 되묻기 50 : 지표 모호 1, 저점 반등은 지표 모호(15·17) 20 : 0으로 한쪽으로 모인다. 즉 같은 표현이 양쪽으로 학습되는 모순이 줄어든다(해석: 모순 해소가 v3의 "값↔지표 되묻기 혼동" 완화에 도움이 될 수 있으나 재학습 전에는 확인 불가).
- v6 전용 haechan 보강의 정답은 `data_fixes`를 통과했다(제외 25건 외 문제 없음).

## C. 이 안으로 해결되지 않는 것 (남는 문제)

1. **지표 모호 되묻기 비중(1,268건)이 그대로다.** v6는 439건, 우리는 1,252건이다. 이 안은 비중을 줄이지 않는다. q4b-v3의 값 되묻기 후퇴가 이 비중 때문이라는 가설(미확인)을 그대로 안고 간다. v4 계획의 "비중 조절 실험"은 별도로 해야 한다. 8B와 같은 데이터를 쓰기로 했으므로, 8B에서도 지표 모호가 3배로 늘어난 데이터가 쓰인다는 점을 haechan이 알아야 한다.
2. **"규모가 큰/작은" 표현이 여전히 둘로 갈린다.** 교체 후에도 지표 모호(8·14) 11, 지표 모호(14·19) 5, 값 되묻기(14) 10이 섞여 있다. 평가 정답은 (14·19)다. haechan도 "기준 충돌"로 분류하고 보류한 항목이다(`LABEL_AUDIT.md` 1절). 팀이 기준을 정해야 한다.
3. **변동성 표현:** 교체 후 값 되묻기(18)로 통일된다(11건). 평가의 "롤러코스터"는 지표 모호(16·18)가 정답이므로 평가와는 반대 방향이다(해석: v6의 결정을 따른 결과이며, 8B도 같은 선택을 학습했다).
4. **외부 LLM 449건(426 반영)의 출처 표기.** 8B에도 쓰려면 팀 정책(외부 LLM 허용, 출처 `_source` 표기)에 따라 그대로 두면 되지만, haechan이 이 데이터를 받아 쓸지 확인이 필요하다.
5. **8B 학습 파일과의 동일성.** haechan의 v6는 `aug6`가 합쳐진 상태이고 8B 학습에 쓴 파일과 같은지 확인되지 않았다. 통합본을 만든 뒤 **같은 sha256 파일을 양쪽이 쓰는지**로 확인해야 한다.

## D. val(검증 세트) 처리
- val은 우리 337, v6 319대화. 문장 기준 공통 250개이고 그중 28개는 정답이 다르다. 33건 유형 충돌 문장은 양쪽 val에 하나도 없다.
- v6 val 중 우리 `data_fixes` 대상은 7건이다.
- 지표 모호 비중이 val에서도 다르다: 우리 72 vs v6 29. val 구성이 다르면 eval_loss를 8B와 직접 비교할 수 없다.
- 제안: **통합 val은 하나로 정한다.** 가장 단순한 것은 v6 val(319)에 `data_fixes`를 적용하고 `label` 키로 맞추는 것이다. 우리 val에만 있는 문장(약 70)은 train 쪽으로 옮겨도 된다(train과 겹치지 않음을 확인).

| 근거 | 내용 |
|---|---|
| 측정이 사라진다 | 111문항은 8B·4B·v1~v7 전부를 같은 기준으로 비교하는 유일한 공통 시험이다. 넣으면 이후 점수가 암기 때문인지 구분할 수 없고, 지금까지의 수치와도 비교가 끊긴다. |
