# Qwen3-8B 파인튜닝 설정 명세 (QLoRA)

> 작성: byungjun / 2026-11-05 / 상태: **제안 (아직 한 번도 돌려 보지 않음)**
> 근거: 병합 데이터(`train.jsonl` 2,090건, `val.jsonl` 111건)와 프로젝트 목적. 수치 중 "경험치"로 표시한 것은 이 데이터로 검증한 값이 아니다. 첫 실행 결과로 조정한다.

## 0. 프로젝트 목적과 이 설정의 기준
**Qwen3-8B는 사용자의 자연어 입력을 원칙값(지표 20개 JSON)으로 매칭하는 "말 번역기"로 쓰이고, 이 과정에서 필요한 쉬운 설명(용어 답변, 설명 말풍선)도 함께 학습한다.**
시뮬레이션 분석 리포트 글쓰기는 다른 LLM(Claude Haiku 5.5 API)이 맡으며, 이 모델의 일이 아니다.
(흐름도 기준: 원칙 만들기, 원칙 수정 두 흐름에서 Qwen3-8B를 쓴다.)

| 일 | 데이터 | 출력 | 성능 기준 |
|---|---|---|---|
| 말 → 지표 20개 JSON (규칙 확정) | SEED | JSON | 지표·부등호·값·단위·source가 **정확히** 맞아야 함 |
| 모호하거나 값이 없으면 되묻기 (다중 턴) | S3 | JSON | 되묻기 여부와 이유·선택지가 맞아야 함 |
| 기존 규칙 수정 | S4 | JSON | 잠긴 지표(locked)를 건드리지 않고 바뀐 것만 반영 |
| 지원 안 하는 요청 거절 | S5 | JSON | 종목 추천·예측 등을 거절 |
| 용어 질의응답 | S6 | 자연어 | 용어 정의·방향(낮을수록 좋다 등)이 마스터와 같아야 함 |
| 설명 말풍선 | S7 | 자연어 | 확정 수치를 쉬운 말로 풀어 쓰되 추천·보장·예측 표현이 없어야 함 |

학습 데이터 전체(2,090건)를 사용한다. 설정 기준은 **JSON 출력의 정확성**이 1순위이고, S6·S7은 마스터와 어긋난 사실이 없는지가 기준이다.

## 1. 모델과 학습 방식
| 항목 | 값 | 이유 |
|---|---|---|
| 기반 모델 | `Qwen/Qwen3-8B` (Hugging Face) | 팀 결정. Ollama용 `qwen3:8b`는 추론 파일이라 학습에 못 쓴다. 가중치를 새로 받는다(약 16GB) |
| 방식 | QLoRA (4비트 nf4 + double quant, 계산은 bf16) | 8B를 16~24GB GPU에서 학습하기 위해. 4080(16GB)과 4090(24GB) 모두 bf16 지원 |
| 사고 모드 | **끈다 (`enable_thinking=False`)** | 정답에 `<think>`가 없다. 학습과 추론에서 같은 방식으로 템플릿을 적용해야 한다 |
| 일반 대화 데이터 혼합 | 하지 않음 | D5(일반 한국어 지시 데이터)는 삭제했다. LoRA는 원 모델을 유지하는 편이지만, 프로젝트 밖 질문에 대한 답 품질은 평가하지 않는다 |

## 2. LoRA 설정
| 항목 | 값 | 이유 |
|---|---|---|
| rank `r` | 32 | JSON 구조와 20개 지표 규칙을 정확히 외우기에 16보다 여유를 둠 (경험치) |
| `lora_alpha` | 64 | `2r`. 변화 크기를 키워 적은 데이터에서도 학습이 되도록 |
| dropout | 0.05 | 데이터가 2천 건대라 약한 정규화 |
| 적용 층 | `q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj` (전부) | 형식 학습은 어텐션만이 아니라 MLP까지 포함할 때 안정적 (경험치) |
| bias | none | |

## 3. 데이터 처리 (성능에 가장 큰 영향)
1. **채팅 템플릿**: Qwen3 템플릿을 `enable_thinking=False`로 적용한다. system 프롬프트는 2종(JSON 변환용 / 설명용)을 **글자 그대로** 쓴다. 추론할 때도 같은 문구를 써야 한다.
2. **loss는 assistant 답변에만**: system·user 토큰은 마스킹(-100)한다.
   - S3는 여러 턴이라 **모든 assistant 턴에 loss**를 준다. 첫 되묻기와 확정 단계 모두 맞아야 하기 때문이다.
   - TRL의 `assistant_only_loss`는 Qwen3 기본 템플릿에 `{% generation %}` 표시가 없어 그대로는 안 된다. 직접 토큰화하며 마스크를 만들거나 Unsloth의 `train_on_responses_only`를 쓴다.
   - **반드시 확인**: 학습 전에 샘플 5건(S3 다중 턴 포함)의 마스크를 출력해서 assistant 부분만 학습되는지 눈으로 본다.
3. **시퀀스 길이 2,048**: 가장 긴 샘플이 약 2,500자(토큰으로는 대략 1,000~1,500, 추정)라 충분하다. 학습 전에 토크나이저로 실제 토큰 수를 재서 **잘리는 샘플이 0건**임을 확인한다.
4. **packing 끔**: 샘플을 이어 붙이면 S3 다중 턴의 경계가 흐려진다. 대신 `group_by_length`로 비슷한 길이끼리 묶어 낭비를 줄인다.
5. **분할은 그대로**: `train.jsonl` / `val.jsonl`은 입력 단위로 나뉘어 있다(겹침 0). 다시 섞지 않는다.

## 5. 평가 (프로젝트 목적에 맞는 기준)
val loss만으로 고르지 않는다. 평가 세트(`hyeonkyeong/data/eval_*.jsonl`, 111건)를 **모델이 직접 생성**하게 해서 본다.

| 지표 | 내용 | 비교 대상 |
|---|---|---|
| JSON 유효율 | 출력이 파싱되는 비율 | 학습 전 Qwen3-8B(zero-shot) |
| 지표 정확도 | 지표 id·부등호·값·단위·source 일치율 | 위와 같음 |
| 되묻기 판단 | 되묻기가 필요한 문장에서 되묻는지, 필요 없는데 되묻지 않는지 | |
| 거절 정확도 | 거절해야 할 요청(S5)을 거절하는지 | |
| locked 보존 | 수정 요청에서 잠긴 지표가 안 바뀌는지 | |
| 설명 품질 (S6·S7) | 출력이 추천·예측 없이 쉬운 말인지 (사람이 표본 확인) | |

- 생성 설정: JSON 출력은 **temperature 0 (그리디)**, 설명은 temperature 0.3~0.5.
- 검증기: haechan의 `validate_data.py`(V1~V10) 규칙을 모델 출력 검사에 재사용할 수 있는지 확인한다.
- **목표치(제안)**: JSON 유효율 99% 이상, 지표 정확도는 학습 전 대비 크게 상승. 구체 수치는 학습 전 기준선을 잰 뒤 팀이 정한다.
- 평가 세트는 학습에 쓰지 않았다(겹치던 S3 6건은 제외). 평가 결과를 보고 데이터를 고칠 때는 평가 문장이 학습에 들어가지 않게 한다.

## 6. 실행 순서
1. **사전 점검** (학습 전, 필수)
   - 토큰 수 분포와 잘림 0건 확인
   - 마스크 샘플 출력 확인
   - 학습 전 모델의 평가 기준선 측정
2. **스모크 테스트**: 50스텝만 돌려 스텝당 시간, 최대 VRAM, loss 하락을 확인한다. 전체 시간은 `스텝당 시간 × 약 524`로 어림한다.
3. **본 학습**: 4에폭, 0.5에폭마다 평가·저장.
4. **선택**: val loss 최저 근처 체크포인트 2~3개를 평가 세트에서 생성 비교해서 하나를 고른다.
5. **배포**: LoRA를 합치고 GGUF(Q4_K_M, 비교용 Q8_0)로 변환해 Ollama에서 쓴다. 어댑터 원본도 보관한다. Ollama의 템플릿과 system 문구가 학습 때와 같아야 한다.

## 9. 값별 선택 이유 보강과 조정 신호
모든 값은 **이 데이터로 검증하지 않은 출발점**이다. "신호"가 보이면 표의 방향으로 조정한다.

| 값 | 선택 이유 (자세히) | 이 값이 틀렸다는 신호 | 조정 방향 |
|---|---|---|---|
| 유효 배치 16 | 2,090건에서 배치가 너무 크면 에폭당 스텝이 줄어 업데이트가 적고, 너무 작으면 loss가 흔들린다. 16이면 에폭당 약 131스텝으로 둘의 중간이다 | loss 곡선이 심하게 흔들림 / 3에폭에도 loss가 거의 안 내려감 | 흔들리면 32로 키우고, 안 내려가면 8로 줄임 |
| 에폭 3~4 | 정해진 JSON 형식은 1~2에폭에 익지만, 값·부등호처럼 틀리기 쉬운 부분은 몇 번 더 봐야 한다. 그 이상은 템플릿 데이터(S6, S7)를 외울 위험이 큼 | val loss가 오르기 시작 / 학습 loss만 계속 하락 | 오르기 시작한 에폭의 직전 체크포인트 선택, 다음 학습은 에폭을 줄임 |
| weight decay 0.01 | LoRA 가중치가 커지는 것을 약하게 막는 일반 값 | 거의 영향 없음 | 과적합이 뚜렷하면 0.05까지 올려 비교 |
| 기울기 클리핑 1.0 | 긴 JSON에서 가끔 생기는 loss 급등이 가중치를 망치지 않도록 하는 안전장치 | 학습 중 loss가 갑자기 치솟음(spike) | 0.5로 낮추고 학습률도 낮춤 |
| `paged_adamw_8bit` | 옵티마이저 상태를 8비트로 저장하고 메모리가 모자랄 때 CPU로 넘겨 16GB에서도 OOM을 피함 | 정밀도 문제는 드묾 | 24GB 여유가 크면 `adamw_torch`로 비교 가능 |
| 워밍업 5% | 처음 몇 스텝에 학습률이 바로 1e-4이면 4비트 가중치 위에서 불안정해질 수 있음 | 초반 loss spike | 10%로 늘림 |
| max_seq_len 2,048 | 가장 긴 샘플이 약 2,500자라 토큰으로 대략 1,000~1,500(추정). 여유를 두고 2,048 | **잘리는 샘플이 1건이라도 있음** (잘리면 JSON이 중간에 끊긴 채 학습됨) | 4,096으로 늘리거나 해당 샘플 확인 |
| r=32 / alpha=64 | 20개 지표의 연산자·단위·기본값처럼 외울 규칙이 많아 용량이 필요함. alpha=2r은 흔한 설정 | 학습 loss는 내려가는데 평가 정확도가 기준선 수준 / 반대로 val loss가 일찍 오름 | 용량 부족이면 r=64, 과적합이면 r=16 |
| 1e-4 | 위 "4. 하이퍼파라미터"와 같음. 데이터가 적고 r이 커서 2e-4보다 보수적으로 시작 | loss가 거의 안 내려가면 너무 낮음 / spike가 있으면 너무 높음 | 2e-4 또는 5e-5로 한 번씩 비교 |
| temperature 0 | JSON은 같은 입력에 같은 출력이어야 하고, 값이 흔들리면 안 됨 | 같은 문장에 매번 다른 지표가 나옴 | 0으로 고정 |

## 10. 예상되는 문제와 대응
| 증상 | 가능한 원인 | 대응 |
|---|---|---|
| CUDA out of memory | 배치·시퀀스 길이가 큼, 다른 사람이 GPU 사용 중(공용 서버) | 배치를 절반으로 줄이고 누적을 2배로, `nvidia-smi`로 다른 프로세스 확인 |
| 학습은 되는데 출력에 JSON 끝이 없음 | 시퀀스가 잘림, 또는 종료 토큰(EOS)이 학습에 안 들어감 | 잘림 0건 확인, assistant 턴 끝의 `<|im_end|>`가 label에 포함되는지 마스크 출력으로 확인 |
| 출력 앞에 `<think>` 빈 블록이 붙거나 사라짐 | 학습과 추론의 `enable_thinking` 설정이 다름 | 학습·평가·Ollama 모두 같은 설정으로 통일 |
| 학습 loss가 비정상적으로 낮음(0에 가까움) | 마스크가 잘못되어 user/system까지 학습(또는 답이 입력에 새어 들어감) | 마스크 샘플 출력 확인 |
| 평가에서 되묻기/거절이 전혀 안 나옴 | S3·S5가 4에폭 동안 안 배워짐, 또는 system 프롬프트를 다르게 넣음 | 추론에서 학습 때 system 문구를 그대로 썼는지 확인 |
| 지표는 맞는데 값·부등호가 틀림 | 값 있는 문장 데이터(S1·S2)가 없어서 학습량 부족 | S1·S2 생성 후 재학습, SEED 가중 시험 |
| 설명(S6·S7)이 항상 같은 말투 | 템플릿 데이터의 문구 중복 | 사람이 표본 확인, 필요하면 S6 중복 제거 후 재학습 |
| GGUF로 변환하니 품질이 떨어짐 | 양자화 손실, 또는 변환 때 템플릿이 달라짐 | Q8_0과 비교, 같은 평가 세트로 다시 측정 |
| 평가 점수만 높고 실제 앱에서 안 맞음 | 평가 세트가 111건으로 작고 우리가 만든 문장 위주 | 실제 사용자 문장을 따로 모아 확인 |
| 서버 접속이 끊겨 학습 중단 | 와이파이/SSH 끊김 | `tmux`에서 실행, 체크포인트에서 이어서 학습 |

## 11. 한계
1. **모든 하이퍼파라미터는 경험치**다. 이 데이터와 이 모델 조합으로 한 번도 돌려 보지 않았다. 학습률·rank·에폭은 첫 실행 결과를 보고 조정해야 한다.
2. **평가 세트가 작다**(111건). 점수가 몇 %p 달라도 우연일 수 있다. 신뢰할 만한 비교는 큰 차이일 때만 가능하다.
3. **S1·S2가 없다.** 핵심 과제의 학습량이 부족하다는 가정이 실제로 맞는지는 학습해 봐야 안다.
4. **토큰 수는 추정**이다. 토크나이저로 재면 시간·메모리 예상이 달라진다.
5. **서버 환경을 아직 못 봤다**(설치된 라이브러리 버전, GPU 사용 중인지 등). 이 PC의 `transformers 5.x`, `trl 1.x` 기준 지식이라 API가 다를 수 있다.
6. **실제 서비스 품질은 평가하지 않는다.** JSON 정확도와 형식은 보지만, 사용자가 쓰는 표현의 다양성을 충분히 다루는지는 별도 확인이 필요하다.
7. 시간 예상(30분~1시간 15분 등)은 처리 속도 추정에 따른 것이고, 스모크 테스트로 확인하기 전까지는 믿을 수 없다.
