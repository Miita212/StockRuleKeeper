# 수정내역

대상: `members/byungjun/backend` (hyeonkyeong 원본의 복사본). 원본과 다른 팀원 폴더는 건드리지 않았다.
GitHub에는 올리지 않는다(사용자 지시).

## 1. 수정 배경

기존 구조는 앱이 요청을 받을 때 한투·DART를 부르지 않고 DB만 읽었다. 외부 API는 관리자가 `batch/build_universe.py`,
`batch/collect_data.py`를 직접 실행할 때만 불렸다. 그래서
- 수집을 안 돌리면 DB가 비어 종목 검색·판정·추천이 모두 빈 결과였고,
- 수집 이후에 바뀐 현재가·거래량은 앱에 반영되지 않았다.

## 2. 바뀐 동작

종목 지표를 계산하기 직전에 **한투·DART에서 최신 데이터를 먼저 받아 DB에 저장하고, 그 DB 값으로 계산**한다.
DB는 저장소(캐시)이자 API 실패 때의 대비책이다.

| 데이터 | 받는 방식 |
|---|---|
| 현재가 스냅샷(한투) | 종목 계산 때마다 받음 |
| 일봉(한투) | DB에 400건 미만이면 760일치, 아니면 마지막 저장일 이후만 |
| 배당(한투) | DB에 없을 때만 |
| 재무제표(DART) | DB에 없는 보고서만(분기마다만 바뀜). 첫 호출에서 corp_code 매핑도 받음 |
| 종목 목록 | 서버 시작 때 `stocks` 표가 비어 있으면 `data/semiconductor_universe.json`(113개)으로 채움 |

같은 종목은 `LIVE_TTL_SEC`(기본 300초) 안에는 다시 받지 않는다. API 호출이 실패하면 오류를 로그(`[live] ...`)에 남기고 DB 값으로 계속한다.

## 3. 파일별 변경

### 새 파일
- `backend/services/live.py`
  - `seed_stocks()`: `stocks` 표가 비어 있으면 종목 풀 파일로 채운다.
  - `ensure_fresh(conn, code)`: 종목 하나의 한투·DART 데이터를 받아 DB에 저장한다. 한투/DART를 각각 try하여 실패하면 DB 값 사용.
  - `_refresh_kis`, `_refresh_dart`: 기존 `batch/collect_data.py`의 `collect_dart`와 `external/kis/quotes.py`를 그대로 재사용한다.

### 수정한 파일
- `backend/config.py`: 설정 2개 추가
  - `LIVE_FETCH`(기본 `1`): `0`이면 예전처럼 DB만 읽는다.
  - `LIVE_TTL_SEC`(기본 `300`): 종목별 재수신 간격(초).
- `backend/indicators/compute.py`
  - `load_inputs()` 맨 앞에서 `ensure_fresh()`를 호출한다. 종목 목록·판정서·시뮬레이션이 모두 이 함수를 거치므로 한 곳 수정으로 전부 적용된다.
  - 모듈 설명 문구를 현재 동작에 맞게 고쳤다.
- `backend/services/stocks.py`
  - 계산 결과 캐시를 "하루(날짜 비교)"에서 `LIVE_TTL_SEC`초(시간 비교)로 바꿨다.
  - 모듈 설명 문구 수정, `date` import를 `time`으로 교체.
- `backend/main.py`: 서버 시작(lifespan)에서 `init_db()` 뒤에 `seed_stocks()`를 호출한다.

### 바꾸지 않은 것
- `batch/*`(수집 스크립트)는 그대로다. 필요하면 여전히 미리 채울 수 있다.
- `api/`, `indicators/judge.py`, `indicators/calc_*.py`, `external/*`, `db/*`.

## 4. 실행 설정 (파일이 아니라 실행 때 환경변수)

```
EXTERNAL_MODE=live LLM_PROVIDER=qwen_base LOCAL_LLM_MODEL=qwen3:8b \
  ~/.venvs/stockrulekeeper/bin/python -m uvicorn main:app --host 0.0.0.0 --port 8000
```
`.env`는 수정하지 않았다. 파인튜닝 전 `qwen3:8b`는 `LLM_PROVIDER=qwen_base`(Haiku와 같은 상세 프롬프트를 Ollama로 호출)로 연결했다.

## 5. 확인한 결과

- 서버 시작 시 `stocks` 0건 -> 113건.
- `GET /stocks/005930/verdict?principle_id=1`: 12초, 통과 15/20. 이후 DB에 일봉 507건, 스냅샷 1건, 배당 32건, 재무 9건, corp_code 4,013건이 저장됨.
- 종목 목록(`GET /stocks`)과 시뮬레이션은 변경 후 호출해 보지 않았다.

## 6. 한계와 주의

- **첫 호출이 느리다.** 종목 하나의 첫 수신이 약 12초(삼성전자 기준)다. 종목 목록은 113개를 모두 계산하므로 **처음 열 때 수십 분이 걸릴 수 있고**, 브라우저가 먼저 시간 초과될 수 있다. 한 번 받은 종목은 DB에 남아 이후에는 스냅샷·최근 일봉만 받는다(종목당 약 2회 호출 x 0.6초 간격 = 목록 전체 약 2분, TTL마다 반복).
- 시뮬레이션도 `load_inputs`를 거치므로 113개 종목을 순회하며 같은 비용이 든다.
- 호출 한도 방어(`KIS_MIN_INTERVAL` 0.6초)는 그대로라 사용자가 동시에 여러 화면을 열면 서로 기다린다.
- 실계좌 한투 키와 DART 키로 실제 호출이 나간다.
- API 실패를 삼키고 DB 값으로 대체하므로, 화면 값이 최신이 아닌 경우를 알리는 표시는 없다(로그에만 `[live]` 남김).
- 종목 풀은 파일(`data/semiconductor_universe.json`)을 쓰며, 종목 목록 자체를 API로 새로 만드는 것은 아니다(`batch/build_universe.py` 약 30분 작업).

## 7. 되돌리는 방법

- 동작만 끄기: 실행 환경에 `LIVE_FETCH=0`.
- 코드 되돌리기: `services/live.py` 삭제 후 위 3번의 수정 파일 4개에서 `ensure_fresh`/`seed_stocks`/`LIVE_*` 부분을 제거(원본은 hyeonkyeong의 `members/hyeonkyeong/backend`).

# 2차 수정: 검색한 종목만 API로 받기

## 배경
1차 수정은 종목 계산마다 API를 불러서, 종목 검색 화면이 열리자마자 요청하는 "전체 목록"(반도체 113개)이 113개 종목을 한투·DART에서 받느라 오래 걸렸다. 그동안 검색 결과가 비어 보였다. 화면은 검색어를 서버에 보내지 않고 전체 목록을 받은 뒤 화면에서 걸러내고 있었다.

## 바뀐 동작
| 요청 | 데이터 출처 |
|---|---|
| 종목 검색(`GET /stocks?q=...`) | **검색에 일치한 종목만** 한투·DART에서 받아 DB에 저장하고 판정 |
| 판정서(`GET /stocks/{code}/verdict`) | 그 종목만 API로 받아 판정 |
| 전체 목록(`GET /stocks`, q 없음), 추천(`/stocks/recommend`) | API 호출 없음, DB 값만 |
| 시뮬레이션 | API 호출 없음, DB 값만 (1차 수정에서는 113개를 API로 받았음) |

받는 항목은 20개 지표 계산에 필요한 것만이다(한투: 현재가 스냅샷·일봉·배당, DART: 재무제표). 종목 기본정보/업종 등 지표에 쓰이지 않는 호출은 하지 않는다.

## 파일별 변경
- `backend/indicators/compute.py`: 1차에서 넣은 `ensure_fresh` 호출과 import를 제거(DB 계산 전용으로 되돌림). 설명 문구 수정.
- `backend/services/stocks.py`
  - `actuals(conn, code, live=False)`: `live=True`일 때만 `ensure_fresh`로 API를 먼저 받고 캐시를 건너뛴다.
  - `stock_card(..., live)`, `list_stocks`: `q`가 비어 있지 않을 때만 `live=True`.
  - `verdict`: 항상 `live=True`.
- `frontend/src/api/index.ts`: `searchStocks(principle, q)`가 검색어를 `q`로 서버에 보낸다.
- `frontend/src/screens/S03_StockSearch.tsx`: 화면 진입 시 전체 목록 요청을 없앴다. 검색어 입력이 0.5초 멈추면 그 검색어만 서버에 보내고(이전 응답은 무시), 서버가 찾은 종목을 그대로 보여 준다. 추천 목록은 그대로.

## 확인한 결과
- `GET /stocks?q=005930`: 삼성전자만 반환, 약 1초(이미 DB에 있는 항목은 스냅샷·최근 일봉만 갱신). 등락률이 -7.57% -> -6.65%로 바뀌어 새 값이 반영됨.
- `GET /stocks?principle_id=1`(전체 목록): 0.01초, API 호출 없음.
- 프론트 `tsc --noEmit` 오류 없음.

## 한계
- 전체 목록·추천·시뮬레이션은 DB에 저장된 종목만 보여 준다. 처음에는 검색·판정한 종목만 DB에 쌓이므로, 추천이 적게 나오고 시뮬레이션 대상 종목이 적을 수 있다. 전체를 채우려면 `batch/collect_data.py`를 돌려야 한다.
- 처음 검색하는 종목은 DART 재무제표까지 받아 약 12초가 걸린다. 두 번째부터는 약 1초.
- "삼"처럼 짧은 검색어는 여러 종목이 일치해 각 종목을 받느라 오래 걸린다.

# 3차 수정: 원래 방식 복원 + 한투만 API 우선 + DB 전체 채우기

## 요청
- 2차 수정(검색한 종목만 받기)을 되돌려 **원래 방식**(반도체 113개 전체를 판정해 원칙 충족 종목을 목록·추천으로 만든다)으로 돌린다.
- 검색하면 내가 검색한 종목은 그대로 떠야 한다.
- DB에 반도체 113개 관련 데이터를 전부 채운다.
- **DART 데이터는 DB에서 읽고, 한국투자증권 데이터는 API를 무조건 우선**한다.

## 바뀐 동작
| 항목 | 출처 |
|---|---|
| 종목 목록·추천·검색·판정서 | 반도체 113개 전체(또는 검색 대상)를 판정. 입력은 아래 두 줄 |
| 한투 데이터(현재가 스냅샷·일봉·배당) | **요청 때 API 먼저**, 받은 값을 DB에 저장 후 사용 |
| DART 재무제표 | **DB 값만** 사용(요청 때 DART 호출 없음) |
| 시뮬레이션 | DB 값만(2차와 동일) |
| 검색 | 화면이 전체 목록을 받아 종목명·코드로 걸러냄(원래 방식). DB에 113개가 채워져 있으면 검색한 종목은 그대로 뜬다 |

## 파일별 변경
- `frontend/src/api/index.ts`, `frontend/src/screens/S03_StockSearch.tsx`: 2차 수정을 되돌림(검색어를 서버에 보내지 않고, 진입 시 전체 목록·추천을 받아 화면에서 검색).
- `backend/services/stocks.py`: `live` 인자를 모두 제거. `actuals()`는 캐시(`LIVE_TTL_SEC`)에 없으면 `ensure_fresh()`로 한투를 받은 뒤 DB로 계산. 모든 경로(목록·추천·판정서)가 같은 방식.
- `backend/services/live.py`
  - DART 갱신(`_refresh_dart`)과 corp_codes 로딩을 제거했다(DB 전용).
  - 목록과 추천이 동시에 요청돼도 같은 종목을 두 번 받지 않도록 잠금(`_lock`)을 넣고, TTL 검사를 잠금 안에서 한다.
  - 오류 로그 문구를 `[live] 한투 ...`로 바꿨다.
- `backend/indicators/compute.py`: 변경 없음(2차에서 DB 계산 전용으로 되돌린 상태 유지).

## DB 채우기
- `batch/collect_data.py`(전체)를 실행해 반도체 113개의 한투(일봉 760일·스냅샷·배당)와 DART(재무제표) 데이터를 `backend/data/stockrule.db`에 저장한다.
- 수집 중에는 한투 호출 한도를 같이 쓰지 않도록 백엔드를 껐고, 수집이 끝난 뒤 다시 켠다.
- 실패한 항목은 `backend/.cache/collect_errors.json`에 남는다.

## 한계
- 목록·추천 화면을 처음 열면 113개 종목의 한투 데이터(스냅샷+최근 일봉, 종목당 약 2회 호출 x 0.6초)를 먼저 받으므로 **약 2~3분**이 걸린다. 그동안 목록이 비어 보인다. 이후 `LIVE_TTL_SEC`(300초) 안에는 즉시 나온다.
- 한투 장애나 한도 초과 시 해당 종목은 DB의 마지막 저장값으로 판정한다(화면에 표시는 없고 로그에만 남음).
- DART 재무는 수집 시점 값이다. 분기 보고서가 새로 나오면 `batch/collect_data.py`를 다시 돌려야 반영된다.
- 이 파일은 `수정내역.md`다. 요청에 `수정사항.md`로 적혀 있었으나 같은 파일에 이어서 기록했다.

## 3차 수정 추가: 종목 검색 결과를 15개씩 페이지로 표시

- 요청: 검색은 전 종목 대상이되, 113개를 한꺼번에 띄우지 않고 충족 지표가 많은 순으로 15개씩 보여 준다(페이지 번호 방식).
- `frontend/src/screens/S03_StockSearch.tsx`
  - 검색 결과(`found`)를 15개씩 잘라 현재 페이지(`page`)만 표시한다. 정렬은 서버가 이미 충족 지표 많은 순(같으면 이름순)으로 보내므로 그대로 쓴다.
  - 목록 위 "N개"는 한 페이지가 아니라 전체 검색 결과 수를 보여 준다.
  - 검색어를 바꾸면 1페이지로 돌아간다. 결과가 15개 이하이면 페이지 번호를 숨긴다.
  - 검색어가 없을 때의 추천 목록에도 같은 방식이 적용된다.
- `frontend/src/App.css`: 페이지 번호 버튼 스타일(`.pager`) 추가.
- 확인: `tsc --noEmit` 오류 없음. 화면에서 직접 눌러 보지는 않았다.

## 3차 수정 결과: DB 수집과 동작 확인

- `batch/collect_data.py` 전체 실행 완료(종료 코드 0, 실패 0건, `collect_errors.json` 비어 있음).
- DB 채워진 종목 수(113개 중): 일봉 113(56,019행), 스냅샷 113, 배당 111, 재무제표 112. 배당·재무가 없는 종목은 해당 정보가 없는 종목으로 보이며, 어느 종목인지는 확인하지 않았다.
- 복원한 코드 확인: `GET /stocks?principle_id=1`이 113개 전부를 반환했다. 첫 호출은 한투를 종목별로 먼저 받느라 **2분 25초**, 그 뒤 `/stocks/recommend`는 0.01초(TTL 안이라 즉시). 한투 호출 실패 로그(`[live]`)는 0건.
- 현재 원칙(id 1)에서는 모든 핵심 지표를 충족하는 종목이 없어 추천 목록은 빈 목록이다.
