# UI 및 백엔드 수정 내역

Claude Code가 읽는 자료다. UI 작업은 Figma("UI 병준 수정본" 페이지)를 먼저 고치고 코드에 반영한다. 큰 항목마다 번호를 붙이고, 새 수정은 번호를 이어서 추가한다.

## 읽는 법

- 각 항목의 "변경 파일"에 **[프론트]** 와 **[백엔드 ⚠️]** 로 나눠 파일 경로와 무엇을 바꿨는지 적는다.
- **[백엔드 ⚠️]** 는 백엔드 코드를 바꾼 곳이다. 백엔드는 `members/byungjun/backend/`, 프론트는 `members/byungjun/frontend/` 기준 경로다.
- 백엔드는 `uvicorn`을 `--reload` 없이 실행하므로, 백엔드 수정은 서버를 다시 시작해야 반영된다.
- 번호가 붙은 수정 작업은 위 "수정 범위 요약" 표에 모은다. 번호가 없는 설계 판단 기록(예: 문서 맨 끝의 "[별도 정리] 시뮬레이션 분석 리포트에 Haiku를 쓰는 이유")은 표에 넣지 않고 맨 끝에 따로 둔다.

## 2. 대화로 정한 지표를 "해당 지표"로 따로 표시

- **목적**: 02 원칙 세팅에서 20개 지표가 정해진 순서로 전부 나열되어, 방금 대화로 어떤 지표를 어떤 값으로 정했는지 알기 어려웠다. 대화로 정한 지표를 맨 위에 따로 보여준다.
- **기준**: 서버가 내려주는 지표별 `source` 값. `user`·`inferred`는 대화로 정한 지표, `default`는 기본값 지표다. 백엔드 수정은 없다.
- **Figma**: "UI 병준 수정본" 페이지의 02 원칙 세팅 화면 4종(02, 02-2, 02 기존 사용자 · 5단 바, 02 로딩 시안)에 반영했다.

### 화면 구성 (`src/screens/S02_PrincipleSetup.tsx`)

1. **해당 지표 · n개** 구역이 맨 위에 나온다. 파란 테두리 카드로 표시한다.
2. **그 외 지표 · m개** 구역이 그 아래에 나온다. 기존 카테고리별 순서는 유지하고, 값 글자색만 연한 회색으로 한다. 안내 문구는 "기본값이에요. 종목 조건에는 넣지 않아요".
3. 해당 지표가 0개이면 두 구역 제목을 모두 숨기고 예전처럼 카테고리별로만 보여준다. 기본값 지표가 0개이면 "그 외 지표" 제목만 숨긴다.

### 수정 흐름(02-2)에서 "방금 바꾼 지표" 강조

- "해당 지표"에는 정해진 지표 전체를 보여주되, 그중 방금 바꾼 지표는 맨 위에 따로 강조한다.
  - 방금 바꾼 지표: 파란 테두리와 연한 파란 배경, "방금 바꿨어요" 표시, 바꾸기 전 값("이전 150% 이하")을 취소선으로 함께 표시한다.
  - 이전부터 정해 둔 지표: 연한 테두리로 보여준다.
- 방금 바꾼 지표의 기준은 저장된 원칙과 비교해서 정한다. 값이 달라졌거나, 기본값이던 지표를 새로 정한 경우다. 저장 전까지 여러 번 대화로 고쳐도 저장된 원칙 대비 달라진 지표 전체가 표시된다.

## 3. 기본값 지표를 원칙에 포함할지 고르는 스위치

- **목적**: 지금까지는 대화로 정하지 않은 지표도 기본값으로 채워져 항상 20개 지표가 원칙에 들어갔다. 사용자가 기본값 지표를 원칙에 담을지 말지 고르게 한다.
  - 포함(ON, 기본): 20개 전체가 원칙에 들어간다. 이전과 같은 동작이다.
  - 제외(OFF): 대화로 정한 지표(`source`가 `user`·`inferred`)만 n개로 원칙에 들어간다. 판정서, 종목 목록의 충족 개수(`원칙 14/n개 충족`), 시뮬레이션도 n개 기준이 된다.
- **Figma**: "UI 병준 수정본" 페이지의 02 원칙 세팅 화면 4종에 스위치(ON 상태)를 넣었고, OFF 상태 시안 1장("02 원칙 세팅 · 기본값 지표 제외 (토글 OFF)")을 맨 아래 행에 따로 두었다.

### 화면 구성 (`src/screens/S02_PrincipleSetup.tsx`)

- "그 외 지표 · m개" 구역 제목 오른쪽에 **"원칙에 포함" 스위치**가 있다. 안내 문구는 ON일 때 "원칙에 함께 담을까요?", OFF일 때 "원칙에 담지 않아요. 판정서에도 안 나와요".
- OFF이면 기본값 지표 카드와 카테고리 제목이 흐려지고 잠금 버튼을 누를 수 없다.
- 해당 지표가 0개이거나 기본값 지표가 0개이면 이 구역(스위치 포함)이 보이지 않는다.
- 스위치 초기값: 새 원칙은 ON. 저장된 원칙을 고치는 중(02-2)이면 그 원칙이 `source: "default"` 지표를 담고 있었는지로 정한다. 담고 있으면 ON, n개만 담고 있으면 OFF.
- 스위치를 꺼도 화면의 초안(`draft`)에는 20개가 그대로 있다. 대화로 수정할 때 서버에 20개를 모두 보낸다. 저장(`approve()`)할 때만 OFF이면 `source`가 `default`인 지표를 빼고 보낸다.
- 02-2에서 저장하면 "원칙 수정 완료"(S14)에 보이는 변경 목록은 저장하는 지표 중 값이 달라진 것만 보여준다. 이전 원칙에 없던 기본값 지표는 제외하고, 새로 정한 지표는 이전 값을 "없음"으로 표시한다.

### 변경 파일

**[백엔드 ⚠️]**

- `backend/services/principles.py` 의 `normalize()`: 기본값 지표를 뺀 n개짜리 원칙을 `base`로 받으면 `current[ok["id"]]`에서 `KeyError`가 났다. `base`에 없는 지표를 대화로 새로 정하는 경우다. 그래서 기본값 20개(`default_indicators()`)를 먼저 깔고 그 위에 `base`를 덮어쓰도록 바꿨다. 이제 응답의 `indicators`는 항상 20개이고, `base`에 없던 지표는 `source: "default"`로 채워진다.
  - 그 외 백엔드 코드는 바꾸지 않았다. 원칙 저장(`save`, `new_version`)은 받은 지표 목록을 그대로 저장하고, 판정(`judge_stock`), 종목 목록(`stock_card`), `core_ids`는 지표 개수에 상관없이 동작한다.

**[프론트]**

- `src/screens/S02_PrincipleSetup.tsx`: `includeDefaults` 상태, 스위치 UI, 저장할 때 기본값 지표 제외, S14에 넘길 변경 목록 계산 수정.
- `src/components/IndicatorCard.tsx`: `mark`에 `"off"` 값 추가(흐리게 표시).
- `src/App.css`: 스위치(`.switch`, `.switch-box`), 흐린 카드(`.mark-off`, `.category.off`), 구역 제목 배치(`.zone.rest`) 스타일 추가.

## 7. 06 원칙 리스트: 하단 바 가림 오류 수정과 5개씩 페이지

- **문제**: 원칙이 많으면 카드가 하단 메뉴 바 위로 겹쳐 보였다.
- **원인**: 6번에서 카드에 `position: relative; z-index: 1`(밀어서 삭제 버튼 아래로 깔기 위해)을 줬는데, 하단 바(`.nav`)는 `z-index`가 없어서 카드가 바보다 앞에 그려졌다. 바는 `.content` 바깥의 형제 요소라 `.content`가 스크롤돼도 카드가 바 위로 올라왔다.
- **해결**: `.nav`에 `z-index: 10`을 줘서 하단 바가 항상 맨 앞에 오고, 스크롤되는 카드는 그 뒤로 가려진다. 5단 바를 쓰는 다른 화면도 같은 바라 함께 적용된다. 3단 바(`NavSim`)도 같은 `.nav` 클래스를 쓴다.
- **Figma**: "UI 병준 수정본" 페이지 맨 아래 행(y=8700)의 "06 원칙 리스트 · 다른 원칙 7개 (1/2 페이지)", "(2/2 페이지)".
- **페이지 규칙**: "내가 만든 다른 원칙"이 **5개를 넘으면** 5개씩 페이지로 나눈다. 현재 적용 중인 원칙은 항상 맨 위에 고정이고 페이지에 포함하지 않는다. 5개 이하이면 페이지 이동 표시는 나오지 않는다.
- **페이지 이동**: "내가 만든 다른 원칙" 줄 오른쪽의 `‹ 1 / 2 ›`. 첫 페이지에서는 ‹, 마지막 페이지에서는 ›가 비활성이다. 페이지를 옮기면 밀려 있던 카드는 닫힌다. 원칙을 지워 페이지 수가 줄면 마지막 페이지로 간다. 이동 표시를 제목 줄에 넣어 카드 5개가 하단 바 위에 딱 들어가도록 했다.

## 9. 06 원칙 리스트: 긴 원칙명 자동 스크롤 (끝에서 정지)

### 동작

- 이름이 표시 영역보다 **길 때만** 움직인다. 짧으면 그대로 있다.

- 이름을 고치는 중(입력칸)에는 적용되지 않는다.
- **원칙명 글자수 한도를 20자 → 30자(1.5배)로 늘렸다.** 이름 고치기 입력칸의 `maxLength`를 바꿨다(`S06_PrincipleList.tsx`). 이름이 길어질 수 있어 자동 스크롤이 쓰인다. 서버(`backend`)에는 이름 글자수 제한이 없어서 고칠 곳이 없다. 이 변경은 Figma 시안에 반영하지 않았다(입력칸 글자수 제한이라 화면 모양은 같다).

## 11. 02 원칙 세팅: 방금 설정된 지표에 빛 효과 + 영업이익 기본값 변경

- **목적**: 대화를 거듭하며 "해당 지표"의 파란 테두리 카드가 쌓이면 어떤 것이 방금 정해졌는지 알기 어렵다. 방금 정해지거나 바뀐 지표만 파란 테두리에 은은한 빛이 나게 한다.
- **Figma**: "UI 병준 수정본" 페이지 맨 아래 행(y=10700)의 "02 원칙 세팅 · 처음 만든 직후 (3개 모두 빛남)", "02 원칙 세팅 · 대화 후 (방금 바뀐 지표만 빛남)".

## 15. 지표 비활성화 (꾹 눌러 / 말로)

- **목적**: 대화로 정해진 지표를 빼고 싶을 때 쓸 방법이 없었다. 정한 지표를 **비활성화**(= 기본값으로 되돌려 "그 외 지표"로 보냄)할 수 있게 한다.
- **Figma**: "UI 병준 수정본" 페이지 맨 아래 행(y=13700)의 "15-1 지표를 꾹 누르는 중", "15-2 비활성화 확인 창", "15-3 비활성화 후", "15-4 말로 비활성화", "15-5 원칙 수정 · 비활성화 후", "15-6 지표값 상세 시트 · 꾹 눌러 비활성화 확인 창".
- **대상 화면**: 원칙 만들기·고치기 대화 화면(02·02-2·5단 바 버전)의 지표 카드, 그리고 **원칙 관리 → 원칙 수정 → "내가 설정한 지표값 상세보기" 시트**의 지표 카드.

### 동작

- **꾹 누르기**: 정한 지표 카드(대화로 정한 지표 = 해당 지표, 고치기에서는 바뀐 지표와 "그 외 지표"를 펼쳤을 때 보이는 이전에 정한 지표, 시트에서는 "내가 정한 지표")를 **600ms 이상** 누르고 있으면 확인 창이 뜬다: **"지표를 비활성화 하시겠습니까?"** / "부채비율 지표를 '그 외 지표'로 옮기고 기본값으로 되돌려요." / 취소·**비활성화**(빨강). 기본값 지표 카드는 꾹 눌러도 아무 일도 없다. 손가락이 10px 넘게 움직이면 취소하고, 꾹 누른 뒤 이어지는 클릭(수치 입력 등)은 막는다.
- **비활성화**를 누르면 그 지표가 **기본값**(연산자·값·단위)으로 돌아가 `source: "default"`가 되고 자물쇠도 풀리며, **"그 외 지표"** 쪽으로 옮겨진다. 대화에는 "○○ 지표를 비활성화했어요" 말풍선과 "부채비율 100% 이하 → 100% 이하 (기본값)" 한 줄 요약이 쌓이고 지표 카드가 새로 나온다(바뀐 값이 "그 외 지표"로 이동한 모습).
- **입력창에 말로 해도 같다**: "○○는 사용하고 싶지 않아", "○○ 버려줘", "○○ 삭제해줘", "○○는 비활성화해줘" 같은 말을 입력하면 모델에 보내지 않고 **같은 확인 창**이 뜬다(`src/data/deactivate.ts`). 한 번에 여러 지표를 말해도 된다("부채비율이랑 PER 삭제해줘" → 한 창에서 같이 비활성화). 이때 취소하면 "그대로 둘게요" 말풍선이 나온다.
  - 지표 이름과 자주 쓰는 말(PER, PBR, EBITDA, 시총, 배당수익률 등)을 알아본다. 긴 이름이 먼저 잡혀서 "영업이익 증가율"이 "영업이익"으로 오인되지 않는다.
  - "빚 많은 회사는 제외할래요"처럼 조건을 정하는 말은 해당 표현이 없어서 지금처럼 모델이 처리한다(`제외`, `빼`는 일부러 넣지 않았다).
  - 이미 기본값인 지표를 말하면 "이미 기본값(그 외 지표)이에요", **잠근 지표**를 말하면 "잠겨 있어서 비활성화할 수 없어요. 잠금을 풀고 다시 말씀해 주세요"라고 답한다. 꾹 눌러 비활성화하는 것은 잠금과 상관없이 된다(수치 직접 입력과 같은 방식).
  - 정한 지표가 아직 없는 처음 말(새 원칙의 첫 입력)이나 되묻기에 답하는 중에는 이 규칙을 쓰지 않는다.
- 08 시트에서 비활성화하면 시트가 닫히고 대화 화면으로 바뀌어 "이렇게 바뀌었어요!" 카드가 나온다(수치 직접 입력과 같음). 저장은 "이대로 수정할래요"로 한다.
- **저장 때**: 비활성화한 지표는 기본값 지표가 되므로 "원칙에 포함" 스위치를 끄면 원칙에서 빠지고, 켜져 있으면 기본값으로 함께 저장된다(기존 규칙 그대로). 14 화면(수정 완료)의 변경 내용에도 "(이전 값) → (기본값)"으로 나온다.

## 19. 되묻기 중 입력창 잠금 — 한 번에 한 주제 (프론트 코드만, Figma 해당 없음)

### 19-1. 발단: 엉뚱한 되묻기 연쇄

- 테스트 중 대화가 이렇게 흘러갔다. "배당 꾸준한 곳이 좋아" → 모델이 연속 배당 연수 되묻기(버튼 3개) → **버튼을 누르지 않고** "부채가 많은 회사도 싫어"를 직접 입력 → 부채비율 되묻기 → "100% 이하로 보통으로 할래요" 선택 → **이미 고른 뒤인데도** 이자 비용 되묻기 → 다시 선택하자 매출순이익률 되묻기. 답했는데도 되묻기가 끝나지 않고 점점 주제가 엉뚱해졌다.

### 19-2. 첫 번째 시도와 되돌림 (undo)

- **첫 시도**: "되묻기 중 직접 입력한 말이 앞 대화에 이어지는 말이면 맥락을 유지하고, 아니면 앞 맥락을 지운다"로 정했다. 이어지는 말은 "도", "그리고", "또" 같은 이어 붙이는 말과 숫자가 든 답으로 보았다(`PrincipleChat.tsx`의 `send`, `continuesDialog`). 거절 안내가 나오면 구간을 끝내는 것도 넣었다.
- **결과**: 프론트·백엔드를 재시작하고 다시 테스트해도 같은 연쇄가 그대로 반복되었다. 문제가 해결되지 않아 **코드와 문서 모두 되돌렸다**(undo).
- **되돌린 이유(원인 분석)**: 위 시도는 "도"가 든 말("부채가 많은 회사**도** 싫어")을 이어지는 말로 보았다. 바로 테스트에서 문제가 된 입력이었다. 즉 맥락을 이어붙이는 쪽이 원인과 같았다.

### 19-3. 원인 파악

모델(파인튜닝한 Qwen3-8B)에 같은 대화를 직접 보내 확인했다.

- 파인튜닝 데이터에는 **"사용자 말 → 모델 되묻기 → 그 되묻기에 대한 답 → 확정"** 형태만 있다(1~3턴). **"되묻기에 답하지 않고 다른 말이 이어지는"** 형태는 학습한 적이 없다.
- 답하지 않은 되묻기가 대화에 남은 채 새 말이 이어지면 모델이 학습하지 않은 형태를 받게 되고, 그 상태에서 답을 받아도 확정하지 못한다. 대신 관련 있어 보이는 되묻기를 계속 만들어낸다(부채비율 → 이자 비용 → 매출순이익률).
- 같은 말을 새 원칙으로 **처음부터** 보내면 부채비율 되묻기 → 100% 선택 → 바로 확정으로 끝난다. 한 번의 질문과 답 안에서는 문제가 없다.
- 한 문장에 조건 둘("배당 꾸준한 곳이 좋아. 부채가 많은 회사도 싫어")을 보내는 방식도 불안정하다. 순서에 따라 뒤의 조건이 사라진다(배당을 앞에 두면 부채 조건이 사라짐).
- 수정 모드 형식으로 두 번째 조건을 넣으면 되묻지 않고 임의 값(연속 배당 4년)으로 바로 바꾼다.
- 응답 시간은 맥락 누적과 거의 무관하다(시간은 출력하는 글자 수가 좌우). 실제 문제는 속도가 아니라 정확도다. 세션 전체를 쌓는 방식도 학습 형식과 달라 같은 이유로 제외했다.
- 서버 코드는 받은 `history`를 그대로 이어붙일 뿐이라 원인이 서버에 있지 않다.

### 19-4. 최종 결정: 한 번에 한 주제

- **대화 구간**: 되묻기 → 버튼 선택 → 확정까지가 한 구간이다. 구간 안에서만 대화를 이어붙인다(학습한 형태).
- **구간을 섞지 못하게 UX를 제한**: 모델이 선택 버튼을 띄운 동안에는 **채팅 입력창을 잠가서** 다른 말을 입력할 수 없게 한다. 사용자는 위의 버튼 중 하나를 골라야만 다음으로 간다. 그래서 "답하지 않은 되묻기가 남은 채 새 말이 이어지는" 상황이 생길 수 없다.

## 20. 현경 백엔드 수정 4건 반영 + 한투 시가총액 0 처리 (백엔드 위주, 프론트는 등락률 기준 표시만)

## [별도 정리] 시뮬레이션 분석 리포트에 Haiku를 쓰는 이유

> UI·백엔드 수정 작업이 아니라 설계 판단 기록이다. 별도 파일을 만들지 않고 이 문서에 함께 둔다. "Qwen3-8B로 리포트를 대신 쓰면 안 되는가"를 검토한 대화(2026-11-09)를 바탕으로 정리했다. 성능에 관한 내용은 코드와 작업 성격을 보고 한 **추정**이며, 모델끼리 직접 돌려 비교한 결과가 아니다.

### 결론

- **자연어 → 지표 변환은 파인튜닝한 Qwen3-8B, 시뮬레이션 분석 리포트는 Haiku 5.5**로 역할을 나눈다.
- 두 작업은 성격이 달라서, 한 모델로 합치지 않고 각자에게 맞는 모델을 쓴다. **리포트에는 Haiku만 쓰며, Qwen을 대신 또는 함께 쓰지 않는다**(아래 "확정 사항").

### 두 작업의 성격 차이

| | 자연어 → 지표 변환 | 시뮬레이션 분석 리포트 |
|---|---|---|
| 하는 일 | 사용자의 말을 지표 20개 JSON으로 바꿈 | 이미 계산된 결과를 쉬운 문장으로 풀어 설명 |
| 출력 | 정해진 JSON 형식 | 정해진 JSON 형식이지만 안의 내용은 자연스러운 한국어 문장 |
| 어려움 | 말과 지표의 대응, 형식 | 규칙을 지키면서 글을 쓰는 것 |
| 맞는 방식 | 학습 데이터로 형식·대응을 가르치는 파인튜닝 | 규칙 이행과 문장력이 좋은 큰 모델 |

### Haiku를 쓰는 이유

1. **리포트는 규칙을 지키는 능력이 핵심이다.** 입력에 있는 숫자만 쓰기, "어느 쪽이 더 좋다" 결론 내리지 않기, 입력에 없는 원인(뉴스·실적·시장 상황) 설명하지 않기, 종목 추천하지 않기, 쉬운 "~해요" 체로 쓰기가 모두 지켜져야 한다. 이런 부정 조건(하지 말 것)은 작은 모델이 가장 자주 어긴다. 틀린 숫자나 단정은 사용자의 투자 판단에 곧바로 영향을 주므로 어긋남이 적은 모델이 필요하다.
2. **지금 올라가 있는 Qwen 모델로는 리포트를 쓸 수 없다.** 병준·해찬 파인튜닝 모델은 "지표 20개 JSON"만 내도록 학습되어 있어서, 리포트 형식(headline, comparison 등)을 지키지 못하고 지표 JSON이나 되묻기를 내놓을 가능성이 크다. 파인튜닝하지 않은 일반 Qwen3-8B를 따로 올려야 한다.
3. **일반 Qwen3-8B로는 품질이 떨어질 것으로 본다.** 규칙을 자주 어기고, 문장의 자연스러움과 쉬운 설명도 Haiku보다 낮을 것으로 예상한다. 코드에는 안전장치(숫자·금지어 검사 → 최대 2회 재요청 → 고정 문구 템플릿)가 있어 틀린 내용이 사용자에게 가지는 않지만, 모델이 약하면 재요청과 템플릿 대체가 늘어 사용자가 보는 리포트가 단조로워진다.
4. **로컬에서는 느리다.** 리포트 출력은 수백~1천 토큰이라 로컬에서 한 번에 15~30초 이상 걸릴 수 있다(지표 JSON 응답이 13~15초 걸린 측정값을 바탕으로 한 추정). 재요청이 겹치면 더 길어진다. 앞서 측정에서 응답 시간은 입력 길이가 아니라 출력 글자 수가 좌우했다. Haiku는 보통 몇 초다.
5. **로컬 모델로 Haiku급에 가까워지려면 모델이 훨씬 커야 한다.** 30B대 이상이 필요하다고 보는데, 시연에 쓰는 4060에서는 현실적이지 않다. 학습용 4090(24GB)이면 올릴 수는 있어도 시연 환경이 아니다.
6. **파인튜닝으로 8B를 보완하는 방법도 한계가 분명하다.**
   - 정답 리포트 학습 데이터를 Haiku로 만들어야 하므로 품질의 상한이 Haiku 이하다.
   - 조건에 맞는 종목이 0개이거나 값이 비어 있는 드문 입력에서 더 불안정하다.
   - 리포트용 모델이 따로 생겨서 원칙 변환 모델과 번갈아 올려야 하고, 한 모델에 두 작업을 합쳐 학습하면 이미 확정한 원칙 변환 평가 목표(99/90/90)를 흔들 수 있다.
7. **비용이 큰 이유가 되지 않는다.** Haiku 호출 비용은 리포트당 아주 작다. 앞서 정리한 4일 사용 추정이 3,500원~17만원(보수적 가정 포함)이라, 비용 때문에 로컬로 바꿀 이유가 약하다(가격은 시점마다 달라지므로 재확인 필요).

### 코드에 반영된 구조

- `llm/report.py`는 `LLM_PROVIDER` 설정과 상관없이 **항상 Anthropic(Haiku)** 으로 리포트를 요청한다(`provider="anthropic"` 고정). 원칙 변환(`LLM_PROVIDER=local`일 때 Qwen)과 설정이 서로 영향을 주지 않는다.
- 수치는 전부 코드가 계산하고, 모델은 문장만 쓴다. 출력은 JSON 스키마·입력에 없는 숫자·금지어를 코드가 검사하고, 통과하지 못하면 재요청 후 고정 문구(템플릿)로 대체한다.
- Haiku 호출이 실패하거나 키가 없을 때도 템플릿이 쓰인다.

### 확정 사항

- 시뮬레이션 분석 리포트에는 **Haiku만 사용한다.** Qwen으로 대체하거나 Haiku와 함께(병행·대체 경로로) 쓰는 방식은 채택하지 않는다.
- Haiku 호출이 실패하거나 키가 없을 때는 지금처럼 코드의 고정 문구(템플릿)로만 대체한다.
